Data Architecture · MVP

中医AI健康管家 · 数据架构与存储策略

配套《客户端 MVP 开发方案》。回答一个问题:正式 App 的用户数据放在哪里、怎么存、谁能读、何时删。覆盖手机端与云端两层、表结构、同步协议、加密与合规控制。

版本 0.1 · 草案2026-10-14适用:MVP 及 V2 诊所对接

01原则

两层存储:手机本地加密数据库是"工作副本",云端数据库是"真相来源"。本地保证 30 秒打卡和离线可读;云端保证换机不丢、家庭成员跨设备一致、未来对接诊所。

  1. 从第一天按健康数据对待。体质答题包含排便、带下、情绪、过敏等内容,在 CPRA 和 WA My Health My Data Act 下属于敏感健康数据,无论 App 是否称为"医疗"。
  2. 三套存储物理隔离。健康档案、行为分析、模型评估样本分别存放,权限互不相通。分析仓永远不含健康数值;评估集只收 opt-in 样本。
  3. 原始健康数据不出手机。HealthKit / Health Connect 的原始记录只在设备上;云端只存派生值(睡眠小时数、步数)。
  4. 按成员隔离。家庭账户下每位成员有独立数据密钥;撤销授权 = 销毁该成员密钥。
  5. 按 HIPAA 标准建,虽然 MVP 尚非 Business Associate。V2 对接诊所后即成为 BA;现在多做 15%,省掉届时的重构。
  6. 评分引擎是纯函数,客户端与服务端各跑一份。客户端用于即时反馈,服务端用于权威记录;两边结果必须一致,差异即 bug。

03存储分层

手机端

组件选型存什么
加密数据库SQLite + SQLCipher(expo-sqlite)成员、答题、评估、方案、打卡、离线队列;与云端同构的表

健康数据桥react-native-health / Health Connect,只读读取后立即派生,原始记录不保存

云端(AWS us-west-2,签 BAA)

组件选型存什么
健康档案库RDS PostgreSQL,静态加密(KMS)+ 敏感列字段级加密第 5 节全部业务表
认证Cognito 用户池账号、设备、MFA;家庭成员以"关联身份"建模
对象存储S3,服务端加密,预签名链接数据导出包、分享图、方案 PDF
密钥KMS:根密钥 → 账户密钥 → 成员密钥(信封加密)见第 7 节
分析仓独立账号下的 Redshift / Athena + S3去标识化埋点;与健康档案库无网络连通
评估集独立 S3 桶 + 访问审批opt-in 答题样本与中医师标注
审计日志CloudTrail + 应用级日志写入只追加表 / S3 Object Lock所有对健康数据的读写
知识层(非用户数据)PostgreSQL + pgvector,可 CDN 缓存体质规则、食疗、穴位、节气;每条带 source

为什么不用 Firebase / Supabase 作正式架构

两者几天可上线,适合 Beta 前内测。但健康数据需要:签 BAA(Firebase 仅部分产品覆盖)、字段级加密、按成员密钥隔离、分析与档案物理分离。这些在 BaaS 上要绕着做,到 V2 诊所对接时大概率重构。直接用托管数据库 + 自有 API,成本在方案预算的"云基础设施 $8k–12k / 6 个月"之内。

06同步协议

写路径(打卡、答题)

用户操作 → 写本地 SQLite(事务内同时写 sync_queue) → 界面立即更新(客户端评分引擎重算) → 后台:联网且队列非空时,按顺序批量 POST POST /checkin [ {member_id, local_date, item, value, recorded_at}, … ] POST /assessment/answers [ {answer_id, member_id, round, item_id, value, source, answered_at}, … ] → 服务端幂等写入(以 answer_id / 复合主键去重),重算评估,返回权威结果 → 客户端用返回结果覆盖本地缓存;若与本地计算不一致 → 上报 engine_mismatch 事件

读路径

打开 App → 立即渲染本地缓存 → 后台 GET /sync?since=<cursor> 拉取各表增量(成员、答题、评估、方案、打卡) → 合并到本地;游标前移

冲突规则

  • 打卡:同成员、同日期、同项目,recorded_at 最新者胜。多设备同时打卡同一项极少见,接受。
  • 答题:同成员、同轮、同题,answered_at 最新者胜;评估结果永远由服务端按全部答题重算,不合并结果本身。
  • 成员与授权:服务端为准,客户端不离线修改。
  • 方案:只在服务端生成;客户端不写。

失败与重试

  • 队列项指数退避重试,最多 7 天;超期标记 stale 并在设置页提示"有 N 条记录未同步"。
  • 令牌失效 → 刷新;刷新失败 → 保留队列,要求重新登录,登录后继续。
  • 服务端 4xx(校验失败)→ 不重试,记录原因,界面显示该条打卡"未保存"。

07加密与密钥

KMS 根密钥(客户管理,年度轮换) └─ 账户密钥(每个 account 一把,信封加密) └─ 成员密钥(每个 member 一把) └─ 加密该成员所有 🔒 列 撤销成员授权 / 删除成员 → 计划销毁成员密钥(7 天宽限,可撤回)→ 密文不可解 = 数据失效 删除账户 → 销毁账户密钥 → 所有成员数据同时失效;随后 72 小时内物理删除行与备份标记
  • 传输:TLS 1.2+;Beta 后期启用证书固定。
  • 手机端:SQLCipher 数据库密钥随机生成,存 Keychain / Keystore,受设备解锁保护;可选 Face ID / 指纹应用锁;切后台遮罩。
  • 服务端应用层:🔒 列在写入前用成员密钥加密(AES-256-GCM),数据库管理员看不到明文;非 🔒 列(编码、时间戳、状态)明文以便索引与统计。
  • 备份:RDS 自动快照同样受 KMS 保护;密钥销毁后快照中的对应数据同样不可解。
  • LLM 调用:发送给模型的对话内容去掉姓名、邮箱、成员 ID;只带体质编码与会话内上下文。模型侧不保留训练用途(API 默认)。

11待决策

  1. 字段级加密的粒度:成员级密钥(本文方案)安全性最好,但每次读要解密、不能按 🔒 列索引。替代:账户级密钥,实现简单,撤销成员授权时需逐行重加密。建议成员级。
  2. 对话正文保留期:90 天是折中;法务可能建议更短(30 天)或要求用户可随时清空。
  3. LLM 供应商 BAA 时点:MVP 阶段对话已含症状描述,严格说应尽早签;预算与流程允许的话建议 M3 联调前完成。
  4. 评估集 opt-in 的激励:是否给 opt-in 用户正式报告加速等好处——涉及"用利益换健康数据"的伦理与合规审查,建议不做。
  5. 多区域:若 V2 内即需服务中国大陆用户,需另起部署并评估《个人信息保护法》与数据出境规则;本文不覆盖。
