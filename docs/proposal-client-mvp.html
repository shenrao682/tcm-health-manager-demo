Client Proposal · MVP

中医AI健康管家 · 客户端 MVP 方案

言承中医AI大脑服务平台的患者端移动应用。本方案聚焦 iOS / Android 客户端本身:用户看到什么、如何走完关键流程、客户端如何构建。服务端、AI 编排与合规只描述客户端依赖的部分。

版本 0.5 · 草案2026-10-12周期 6 个月依据:《中医AI破局》slide 25–27

01定位与范围

客户端的工作:让用户在 3 分钟内拿到初步体质判断和一份初版方案,在 30 秒内完成每天的打卡,在一周内不知不觉补完正式评估,在任何时候都能一键找到医生。它是诊所的前哨和患者的日常陪伴,不是诊断工具。

演讲稿把患者端描述为"个人与家庭自我健康管理 + 动态家庭健康档案",并列出六个生活方式维度。客户端 MVP 把这个描述落成四个可触达的东西:一份体质报告、一份随节气更新的调养方案、一个每日打卡、一个家庭切换器。所有疾病相关内容在客户端只有一个出口:分流到医生。

客户端做 · In scope

  • 对话式体质辨识与报告页
  • 调养方案:饮食、食疗、作息、运动、穴位
  • 每日四项打卡、提醒、周报
  • 家庭成员档案与切换
  • 养生问答(受约束)与分流到诊所
  • 中英双语、老年友好模式
  • HealthKit / Health Connect 只读导入睡眠与步数
  • 隐私同意、数据导出、账户删除

客户端不做 · Out of scope

  • 症状自查、疾病分型、任何处方展示
  • 舌象/脉象拍摄与判读
  • 医生聊天、视频问诊、预约系统
  • 商城、支付、药膳购买
  • 可穿戴设备写入与实时同步
  • 社区、动态、好友
  • Web 端、平板专属布局

03信息架构

底部导航(4 个 Tab) │ ├─ 今日 当前成员的今日方案摘要 · 打卡入口 · 节气提示 · 提醒 ├─ 我的体质 体质报告 · 历史评估 · 重新评估入口 ├─ 调养方案 饮食宜忌 · 食疗方 · 作息 · 运动 · 穴位 · 来源 └─ 我的 家庭成员 · 问答入口 · 设置 · 隐私与数据 · 联系诊所 全局 ├─ 顶部成员切换器(头像 + 姓名,所有 Tab 可见) ├─ 问答浮层(从「我的」或「今日」唤起,全屏对话) └─ 分流卡片(问答触发时在对话内呈现;「我的」中常驻「联系我的诊所」)

两条结构性决定:

  • 成员切换器放全局而非藏在「我的」。家庭管理者是 P0 用户,切换成员是高频动作;放在顶部让"我现在在看谁"始终可见,避免把父亲的方案误当成自己的。
  • 问答是浮层,不是 Tab。避免 App 变成"聊天机器人"。问答服务于方案与体质内容,从具体上下文(某道食疗方、某个穴位)唤起时自动带入话题。

04核心流程

流程 A · 首次使用到拿到初版方案(目标 ≤ 6 分钟)

启动 → 语言选择 → 三页价值说明(可跳过) → 隐私与同意(三项逐条勾选:隐私政策 / 健康数据用途 / 非医疗建议) → 注册(手机号或 Apple / Google 登录) → 基础信息(出生年、性别、所在地、过敏、孕哺期) → 进入「今日」(此时已可浏览节气、穴位、食疗内容) → 快速初探(10 题,≤ 2 分钟;问卷或对话任选;可跳过稍后做) → 初步体质报告(主体质 + 置信度标签 + "再答约 N 题可确认") → 选目标(1–2 个:睡眠 / 压力 / 消化 / 精力 / 体重) → 生成初版方案(流式;方案页标注「初版 · 基于快速初探」) → 设置提醒(默认按时辰预填,一键确认)
  • 体质评估不是闸门。基础信息之后用户就在 App 里了;初探可跳过,「今日」页会用引导卡持续邀请。
  • 方案生成用流式输出:首个板块 3 秒内可见,全部板块 15 秒内完成。超时显示"稍后在方案页查看",不阻塞。

流程 A′ · 从初步到正式(目标 ≤ 7 天,用户无感)

每日打卡完成 → 追加一张卡「今天 3 道体质小问题」 → 只问尚未判定的子量表;已早停的体质不再出现 → 每答一题后台重算各体质分数区间 → 所有体质判定完成(答完或早停) → 推送「你的正式体质报告已生成」 → 报告页解锁完整雷达图;方案自动升级为正式版,标注与初版的差异 随时可走捷径:「我的体质」→ 一次答完(按子量表分页,只出未判定题)
  • 自适应早停:标准判定是阈值规则(≥ 40 是,< 30 否),每答一题即可算出该体质分数的可达区间;区间落入单一判定区就停止提问,结论与答满 60 题完全一致。按常见答题分布,平均可省 25–35 题。
  • 对话模式的省题来源:一句"我特别怕冷,手脚老凉,一吃凉的就拉肚子"同时覆盖阳虚质 3 题;自由叙述一轮常映射 3–6 题。
  • 初步与正式的区别用标签而非弹窗表达;初版方案已经可用,正式版只是更准。

流程 B · 每日打卡(目标 ≤ 30 秒)

推送通知 → 直达「今日」打卡卡片 → 睡眠:时长滑块 + 质量三选一(已从 HealthKit 预填则只需确认) → 饮食:今日宜忌是否遵循(是 / 部分 / 否) → 运动:分钟数(步数已预填则换算建议) → 情绪:五个表情 → 完成动效 + 一句话反馈 → 返回「今日」
  • 四项可任选其一单独完成,不强制全部。
  • 当天多次打开只显示未完成项。

流程 C · 用户问了医疗问题(分流)

用户输入 "我最近血压 150,该吃什么中药" → 客户端先发给分类接口 → 返回 medical_advice → 对话内显示分流卡片(非弹窗): "这个问题需要医生评估。我可以帮你把症状记下来,带给你的医生。" [记录症状并联系诊所] [了解一般养生知识] → 选前者:症状摘要表单(预填用户输入)→ 显示合作诊所信息 + 一键拨打 / 复制 → 选后者:回到问答,但话题限定为与血压无关的体质养生 紧急关键词(胸痛、呼吸困难、自杀意念等) → 跳过分类,全屏显示 911 / 988 卡片,对话暂停

流程 D · 添加家庭成员

「我的」→ 家庭成员 → 添加 → 成年人:填姓名 + 手机/邮箱 → 发送授权链接 → 对方确认后出现在切换器 → 未成年人:监护人声明 → 直接创建 → 成员卡显示「监护」标识 → 新成员进入流程 A 的"基础信息 → 体质辨识"段

按呈现方式

呈现方式决定导航栈和返回行为,是三类页面最本质的区别:

  • Tab 根页(S01、S04、S06、「我的」列表):点底部 Tab 直达;无返回键;切换 Tab 时各自的栈状态保留。
  • 推入页(S07、S08、S09、S10、S12、S13、S14):从父页面点进去,左上角返回;属于所在 Tab 的导航栈。浏览食疗方时切去打卡再回来,应该还停在那道食疗方上。
  • 模态流程页 / 浮层(S02、S03、S05、S11):从底部弹出,覆盖 Tab 栏。它们是要完成或退出的任务,不是浏览的地方:S02/S03/S05 是"评估 → 选目标 → 生成方案"的线性流程,完成后落到 S06;S11 从多处唤起,关闭后回到唤起它的页面。评估做到一半切 Tab 会丢上下文,所以用模态把用户留在流程里。

  • 删除账户(二次确认,72 小时)
  • 隐私政策、同意记录

06设计原则

  1. 先结论,再解释。体质报告先给名字和一句话,依据折叠;方案先给今天做什么,原理放详情。用户多为中老年,不要让他们读完才知道结论。
  2. 每条建议有出处。来源标签不是装饰,是产品可信度的载体。标签统一样式,点开统一格式(书名 / 标准号 + 章节)。
  3. 医疗边界用界面表达,不靠小字。分流卡片是正式组件,有自己的视觉语言;紧急卡片全屏且不可忽略。免责声明固定在方案底部,不弹窗。
  4. 默认值做足,让确认替代填写。提醒时间按时辰预填,睡眠步数从系统健康读取,目标卡预选最常见项。
  5. 先给价值,再要投入。10 题换一份可用的初版方案;剩下的题拆成每天 3 道,跟着打卡走。永远不把 60 题摆在用户面前。
  6. 双语是两套排版,不是翻译。中文用宋体标题 + 黑体正文,英文用对应衬线/无衬线;体质名英文采用描述式("Qi Deficiency · low energy pattern"),不用拼音。
  7. 老年模式是一等公民。字号 +25%、对比度提升、触控目标 ≥ 48pt、取消手势依赖,所有页面在该模式下必须通过验收。

离线与弱网

  • 已生成的方案、体质报告、本周打卡本地缓存,离线可读。
  • 打卡写入本地队列,联网后同步;冲突以客户端时间戳为准(同一天同一项取最后一次)。
  • 对话与方案生成需要联网;断网时显示明确状态,不显示通用错误。

安全

  • 令牌存 SecureStore;健康数据在 SQLite 中以 SQLCipher 加密。
  • 切后台时遮罩敏感页面(体质报告、家庭成员);支持 Face ID / 指纹作为可选应用锁。
  • 截屏不禁止(老年用户常用截屏分享给子女),但分享图不含姓名。
  • 证书固定(pinning)在 Beta 后期启用,避免早期调试成本。

客户端侧的边界守卫

Guardrails 主体在服务端,客户端承担三件事:

  • 紧急关键词本地词典:无需等待网络即可弹出 911 / 988 卡片。
  • 渲染白名单:对话回答按结构化块渲染(文本、来源、分流卡、紧急卡),不渲染服务端未定义的块类型。
  • 举报通道:长按消息举报,带上下文发给服务端评估队列。

09无障碍与本地化

无障碍

  • 全部页面通过 VoiceOver / TalkBack 走查;雷达图与人体图提供文字替代(各维度分数列表、穴位定位文字)。
  • 动态字体支持到系统最大档;老年模式在此基础上再 +25%。
  • 色彩不作为唯一信息载体:打卡完成同时用图标与文字;雷达图主体质用加粗轴线标注。
  • 所有计时器、动效遵循"减少动态效果"系统设置。

本地化

  • MVP 支持简体中文、英文;繁体中文在 M5 视 Beta 用户构成决定。
  • 体质名、穴位名、节气名使用术语表统一管理,英文采用"描述 + 原名"双写,由英语母语中医师审校。
  • 日期、时辰、单位按地区格式化;时辰提醒在英文界面显示为时间段("9–11 pm · Triple Burner hour")。
  • 中英各自独立的字体与行高 token;中文正文 16/1.75,英文正文 16/1.6。

12风险与决策

风险等级应对
对话式辨识让老年用户困惑,完成率不达标中初探只有 10 题,大幅降低风险;问卷模式始终一键可达;老年模式默认问卷;M1 线框测试含 60 岁以上用户
初步结果不准,用户按初版方案调养后正式报告改判,信任受损中初步结果明确标注置信度与"再答 N 题可确认";初版方案只用主体质通用宜忌,不用兼夹体质细则;M4 用 200 例数据回测初探 10 题对主体质的命中率,目标 ≥ 75%,不达标则调整选题或增至 14 题
日常补完被忽略,大量用户停留在初步状态中小问题卡与打卡绑定,不单独推送;第 5 天起报告页显示"只差 N 题";正式报告解锁完整雷达图与分享作为激励;指标:7 日内正式完成率 ≥ 50%
Skia 人体图在低端 Android 上性能差中M3 在 3 台低端机验证;降级方案为静态 SVG 分经络图
服务端接口延期,客户端无法联调中OpenAPI 先行 + Mock 服务,客户端 M1–M2 完全独立;联调窗口 M3 预留 3 周
HealthKit 权限引发 App Store 审核问题中只读、最小权限、用途说明明确;Beta 用 TestFlight,审核压力低;权限请求放在打卡页首次使用时而非首次启动
分流卡被当成"推销诊所",用户反感中分流卡文案先说"为什么",再给选项;"了解一般养生知识"始终是平等选项;Beta 访谈专门验证
双语内容不同步,英文落后中文低术语表与内容 CMS 强制双字段;缺英文时显示中文并标注,不空白

需要确认的三项决策

  1. 框架:确认 React Native + Expo。替代方案为 Flutter(更好的自绘性能,但团队招聘面窄)或原生双端(成本翻倍)。
  2. 首发语言与平台:确认中文优先、iOS 与 Android 同步,英文在 M4 加入。若 Beta 诊所用户以 iPhone 为主,可考虑 Android 推迟到 M5。
  3. 客户端预算:批准 $314k–$411k,并在 M1 前到位 2 位移动端工程师与 1 位设计师。

本文为客户端视角草案。服务端架构、AI 编排、评估流水线与合规方案见配套文档。预算为区间估算,未含税费与招聘成本。
